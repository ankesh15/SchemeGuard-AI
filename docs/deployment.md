# Deployment procedure and recovery

No live cloud resource was created or changed and no production deployment is claimed. The tested equivalent frontend hosting target is the production Next.js standalone Docker image, alongside persistent Docker API/workers. PostgreSQL/Redis may be managed or maintained privately. All six services are defined in docker-compose.production.yml; the local verification uses separate credentials/volumes and an explicitly trusted test TLS certificate.

## Release

1. Build/tag immutable images from a reviewed commit. Run CI-equivalent lint/type/unit/integration/browser/dependency checks and the synthetic A/B/C demonstration. Back up PostgreSQL, referenced originals and the separate encryption key before changing a deployment.
2. Prepare private `.env.production` from the template. Set real HTTPS origins/hostnames, independent owner/runtime database credentials, stable encryption key and the authorized S3 bucket. For managed PostgreSQL use `DATABASE_URL=postgresql+asyncpg://...?...ssl=require` (or verify-full with correctly installed trust roots) and a distinct `MIGRATION_DATABASE_URL` for owner access. The async and checkpoint drivers map ssl to sslmode consistently. Ensure pgvector can be installed by the migration owner. Managed Redis uses a private rediss URL.
3. Build/start data services only when self-hosting; omit them when configuring managed equivalents through a reviewed host-specific Compose manifest. Never point a first-start PostgreSQL container at an unrelated existing volume. Provision storage with versioning, public access blocked and prefix-scoped IAM. The S3 adapter is implemented and fixture-tested; real IAM/bucket connectivity remains unverified.
4. Run the release commands in docker.md: one owner-only migration command, then runtime grants, then six-service startup. API replicas do not migrate on startup. Existing runtime passwords are not rotated by grants. Explicitly import static metadata with `docker compose --env-file .env.production -f docker-compose.production.yml exec api python -m app.seed`. Do not seed fictional rules into production.
5. Configure an HTTPS edge/load balancer in front of loopback frontend/API ports. Keep DB/Redis unexposed. Frontend browser APIs remain same-origin; `INTERNAL_API_URL` is server-only. Allow exactly the frontend origin in both frontend and backend. TLS terminates at the trusted edge; production cookies are Secure. Backend proxy-header trust is disabled by default; do not accept spoofed forwarding headers.
6. Verify health/readiness, runtime role privileges, cookie/CSRF/role isolation, public search, approved-version selection, object checksums, worker delivery and singleton scheduler. Provision administrators through the existing interactive CLI. Enable monitors only after reviewing exact source access conditions. Missing Gemini credentials must produce a clear unavailable state, never fabricated rules.

Optional Vercel frontend: use the frontend directory, Node 24, `npm ci`/`npm run build`; configure only server-side INTERNAL_API_URL pointing at the HTTPS backend and ADMIN_ALLOWED_ORIGINS matching the Vercel/custom origin. No Gemini/database/storage/encryption keys belong there. Review plan-specific function timeouts for supervised document/workflow routes; persistent Docker frontend hosting avoids those serverless-duration constraints. This Vercel path was documented, not deployed or independently verified.

To switch existing originals to S3, keep local storage active and configure the authorized bucket. Run `python -m app.ops.copy_documents_to_s3` for dry-run checksum checks, then run with `--copy` only with explicit operator authorization to write that bucket. The command copies conditionally and rereads/verifies each object without changing immutable database keys. Back up/verify first, then switch DOCUMENT_STORAGE_BACKEND=s3 on all API/worker services together. Never silently discard local originals.

## Backups, restore and rollback

Use restricted files/secret-managed destination: `docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > private-backup.dump` and `docker compose exec -T api tar -C /var/lib/schemeguard/documents -czf - . > private-documents.tar.gz` for local-volume storage. Set umask 077 first. Back up S3 versions/manifests via an independently controlled bucket/replication policy; preserve every key/checksum referenced by the DB snapshot. Back up PROFILE_ENCRYPTION_KEY separately; it is not recoverable from the database dump. Encrypt backups and test access/retention. Redis is recoverable delivery state; PostgreSQL is authoritative.

Restore into a newly created recovery database first with `pg_restore --no-owner --single-transaction --exit-on-error`, never over the working DB. Restore local originals into a fresh directory (safe tar extraction) or a separately authorized recovery bucket. Compare row counts/hashes, source checksums and private payload decryption with the retained key before switching traffic. Pause schedulers/workers and intake during an actual recovery/cutover; then verify expired leases/outbox delivery and deduplication before resuming. Define RPO/RTO from actual backup schedules; none is invented here.

`python3 scripts/verify_recovery.py` tested this against a UUID-named non-production database and temporary original-document directory, preserving live data. It retains private backups under .local/backups and drops only its own test database. Real managed-service restore/region failover was not exercised.

Prefer forward corrective migrations. Downgrades are destructive and tested only in disposable databases. Before rollback, confirm the previous image understands the current schema/jobs; revert image tags atomically, retain volumes/keys, and rerun health/authorization/version-replay checks. Do not automatically reverse policy publications or rewrite historical reports. No auto-deploy job exists in CI; promotion requires explicit human authorization and verified release artifacts.

## Reproducible local production-profile verification

`python3 scripts/init_production_test.py` creates private `.local/phase7-production.env` once with isolated volume names, independent roles and loopback test origins. It explicitly opts into persistent local filesystem storage solely for this test. Build production images, start db/redis with that env file, then run `scripts/production.py migrate` and `grant-runtime` with the same file before starting all services. `scripts/check_deployment.py --env-file .local/phase7-production.env` checks structural invariants without printing expanded secrets.

For HTTPS, generate a short-lived localhost certificate/key under ignored .local with `openssl req -x509 -newkey rsa:2048 -nodes -keyout .local/phase7-tls/key.pem -out .local/phase7-tls/cert.pem -days 2 -subj /CN=localhost -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'` (create the directory first, umask 077). Run `python3 scripts/local_tls_proxy.py --certificate .local/phase7-tls/cert.pem --key .local/phase7-tls/key.pem` in a separate terminal, then `python3 scripts/verify_production.py --certificate .local/phase7-tls/cert.pem`. Certificate validation remains enabled through the explicitly supplied test trust root. Never use this harness/certificate as a real production edge. Stop it and the isolated test services when done; preserve all volumes.
