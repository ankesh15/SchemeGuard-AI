# Shared authentication and private storage

Phase 6 extends Phase 3's `users`, `login_sessions`, rate-limit and audit tables. Registration always creates a citizen; extra role fields are rejected. Administrator provisioning remains the interactive `python -m app.auth.provision` command. There is no public administrator registration route. Existing admin cookies and endpoints still work; citizen and admin roles are checked independently on every protected API.

Passwords use Argon2id (64 MiB, three iterations, two lanes), with bounded hashing slots and constant-cost dummy verification for unknown names. Sessions use random opaque tokens; only SHA-256 digests are stored. Cookies are HttpOnly, SameSite=Strict, path=/ and Secure in production. Configurable expiration is bounded to 24 hours. Logout revokes the current session; password change revokes every session. Username changes and account deletion require the current password. An active, role-checked owner row is locked during private changes and background reassessment to serialize deletion and updates.

All writes require an explicitly allowed Origin; authenticated writes also require the CSRF token obtained from the current session API. Browser requests go through the fixed-route, same-origin Next.js `/api/account` proxy. It forwards only the session cookie and required headers to the fixed internal API, bounds JSON bodies to 16 KB and applies timeouts. Server-rendered dashboard routes also check the backend session and role. Backend authorization is authoritative, including when APIs are called without the frontend. Auth, private APIs and dashboard responses prohibit caching and framing. Session tokens, passwords, private profiles and reports are never placed in localStorage, public environment variables, tracing, URLs or application logs.

PostgreSQL-backed rate limits bound registration (5/hour per peer address), shared login attempts (configured IP and username windows), password actions and assessment saves. Deployments behind a reverse proxy need a reviewed trusted-proxy/IP configuration; the app does not trust arbitrary forwarded IP headers. This development deployment shares the Next proxy's IP for browser login limiting, so adjust capacity deliberately before serving many people.

`PROFILE_ENCRYPTION_KEY` is a stable Fernet key shared only by API and worker. `python3 scripts/init_env.py` adds one to the ignored local `.env` if absent, without printing or rotating it. Registration/private writes fail closed when it is unavailable. Profiles, minimal assessment inputs, complete reports and reassessment impacts are authenticated encrypted envelopes bound to owner and record purpose. Wrong-key, swapped-owner or corrupt ciphertext fails closed. Rule/scheme references, overall result and account identifiers remain relational plaintext; this is application-level sensitive payload encryption, not full-database encryption. Operators still control database access, disk encryption, TLS, backups and key custody. Back up the key separately from the database. Key rotation requires an explicit decrypt/re-encrypt migration; replacing the key loses access to existing encrypted payloads.

Account deletion requires explicit acknowledgement and password confirmation. It purges profiles, saved assessment chains, reassessment impacts, preferences and notifications, revokes sessions and anonymizes/disables the retained account reference. Government documents, approved policy history and security audit integrity are preserved. Profile deletion alone retains historical encrypted assessment snapshots for reproducibility; subsequent reassessments use the remaining current authorized profile and produce UNKNOWN for missing fields. Backup erasure/retention is an operator responsibility; deleting live rows does not rewrite existing backups. The MVP has no automatic retention expiry, email, identity verification, password recovery delivery or MFA. Password reset is honestly unavailable; do not issue public reset tokens without a verified delivery mechanism.

For production use HTTPS, `APP_ENV=production`, explicit HTTPS `ADMIN_ALLOWED_ORIGINS`, restricted networking, a secret manager, managed key backups and a reviewed retention/backup policy. The current Compose file remains a local hot-reload development configuration.

Phase 7 hardening: in-flight login checks capture the verified hash and recheck it under the account lock before creating a session, so a concurrent password change cannot issue a fresh old-password session. Host headers and all request body sizes are bounded. Next.js auth controls remain disabled until hydration. Production cookies/CSRF/role checks were verified through a local HTTPS harness with an explicitly trusted test certificate. Production runtime DB roles have DML access without migration ownership; encrypted-key and password-reset limitations above still apply.
