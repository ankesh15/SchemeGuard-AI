# Deterministic reassessment after verified publication

The existing human publication transaction now inserts a durable `REASSESS` outbox job in the same transaction as the approved policy change. Rollback publishes neither the rules nor its reassessment request. Redis carries only the durable job UUID. The existing Celery dispatcher, execution lock, finite retry/lease protocol and bounded worker concurrency are reused; no second queue system is introduced. Future-effective policies are scheduled no earlier than midnight Asia/Kolkata on their verified effective date.

Processing rechecks APPROVED status, the published rule reference and effective date, then finds accounts with saved assessments for the scheme before publication. It locks/rechecks each active citizen account before reading private data. It uses the latest saved assessment, its explicit reassessment consent, and the current notification preferences. Material changes with authorization run the unchanged PASS/FAIL/UNKNOWN engine against the necessary fields of the **current stored profile**, not undeclared questionnaire overrides or invented defaults. Deleting the current profile makes missing conditions UNKNOWN. An obsolete queued publication is skipped if a later approved policy already applies.

The old assessment never changes. A new encrypted report/input snapshot pins the new approved rule and records its parent and policy change. An encrypted impact record records old/new outcomes, stable condition differences and missing fields. The generic notification links to the authorized detailed report. Nonmaterial updates or disabled automatic consent can still produce a general verified policy update when preferences permit. There are no fabricated assessments for metadata-only schemes.

Each account commits its assessment, event and notification atomically. Deterministic IDs, uniqueness, an account lock and the durable task lock make retries safe. A crash can leave already completed accounts committed; retry skips them and continues. Deleted/disabled users are never recreated. A corrupt private payload fails closed, with only a safe error class in the job; operators must investigate without printing decrypted inputs. Jobs have a finite attempt budget; they are not infinite retries. Operators can inspect PostgreSQL background_jobs, worker logs, the monitoring dashboard and change review. After correcting configuration or data, create a new explicitly audited retry job with a new dedupe key through the operator procedure below; never change a published policy or historical assessment to make processing succeed.

For an operator recovery, use an authorized backend shell and `services.jobs.enqueue(session, 'REASSESS', 'operator-retry:<change UUID>:<unique ticket>', {'change_id':'<approved change UUID>'})`, add an `audit(...,'reassessment_operator_retry',actor_id,change_id,notes='<ticket>')` event and commit. Check the original failure first and keep the retry ticket unique. Automatic scheduling/consent remains rechecked. No profile is placed in this payload. The development app does not yet provide an admin reassessment-job recovery UI.

Saved assessments store an encrypted minimal input snapshot, encrypted complete trace/evidence report, engine version marker, original evaluation date, policy ID and timestamp. GET `/assessments/{id}` returns the stored historical report. POST `/{id}/reproduce` evaluates the original snapshot against that exact approved version, bypassing later replacement selection, and compares result and full requirement traces. Metadata-only historical UNKNOWN reports remain UNKNOWN even if a policy is approved later. These replay checks do not call Gemini or RAG. Engine behavior changes require a deliberate compatibility/version migration; the current immutable engine is deterministic-v1.

The first implementation processes accounts sequentially per publication with per-account transactions; worker concurrency is bounded to two, with task timeouts and finite leases. Large deployments should shard publication/account ranges and add an operator recovery dashboard before high-volume use. No high-volume load benchmark or external delivery service was executed.
